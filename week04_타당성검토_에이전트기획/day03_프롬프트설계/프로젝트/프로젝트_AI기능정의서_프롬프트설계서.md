# Day 03 프로젝트 실습

## 건강한하루 AI 기능 정의서 & 프롬프트 설계서 작성

> Day01에서 "검증 필요"로 채택된 **RF-3.0 AI상담(RAG FAQ)** 을 대상으로, 이 기능이 실제로 무엇을 하는 AI인지(`AI 기능 정의서.xlsx`)와 어떤 프롬프트로 동작해야 하는지(`프롬프트 설계서.xlsx`)를 문서화합니다.

---
## 실습 목표
- Day01 ROI 검토 결과를 근거로 RF-1~4 중 왜 RF-3만 AI로 채택됐는지 재확인한다.
- 채택된 AI 기능(RF-3)의 사용자 상황·역할·입출력·자동화 수준을 정의한다.
- `프롬프트 설계와 AI 기능 정의.md`에서 배운 System/User Prompt 개념을 실제 프롬프트 문장으로 작성한다.
- 예외 처리·품질 기준·테스트 케이스로 "좋은 답변"의 기준을 팀이 공유할 수 있게 만든다.

---
## 실습 흐름
```
Day01 AI 기능 기획 및 ROI 검토 확인 (RF-3 채택)
  ↓
AI 기능 정의서 작성 (무엇을 하는 AI인가)
  ↓
프롬프트 설계서 작성 (어떤 규칙으로 말하게 할 것인가)
  ↓
System Prompt / User Prompt 예시 작성
  ↓
출력 형식 · 예외 처리 · 품질 기준 정의
  ↓
테스트 케이스 준비 (다음 실습에서 실제 모델로 검증)
```

## 표지_개요 — 왜 RF-3만 대상인가
- **문서 목적** : Day01 AI 적용 가능성·ROI 검토 결과를 바탕으로, 실제로 만들 AI 기능의 역할·입력·출력·예외·품질 기준을 정의
- **적용 범위** : RF-3.0 AI상담(RAG FAQ) — Day01 검토에서 "검증 필요"로 채택된 **유일한** AI(LLM) 기능
- **참고 문서** : 요구사항정의서.xlsx / Day01 ROI 검토 / 화면설계서.xlsx / 프롬프트 설계서.xlsx

| 항목 | 내용 |
| --- | --- |

## 데이터소스 — RAG 코퍼스는 새로 만들지 않는다

| 데이터(테이블) | AI가 근거로 사용하는 컬럼 | 비고 |
| --- | --- | --- |
| 상품마스터 | 기능성_내용, 섭취량_섭취방법, 섭취시주의사항 | Week02 backend DB 재사용 |
| 영양소_기능성_추천DB | 기능성, 근거_설명, 근거_수준, 출처 | 근거 수준 낮은 항목도 그대로 노출 |
| 영양소별_권장섭취량 | 권장섭취량, 상한섭취량, 단위, 출처 | 섭취량 계산은 규칙 기반, AI는 설명만 생성 |

> 새 데이터를 수집하지 않고 **Week02에서 이미 구축한 DB를 그대로 RAG 코퍼스로 재사용**합니다. 데이터 준비 비용이 이미 0에 가깝다는 것이 RF-3이 채택된 이유이기도 합니다.

## 예외처리_정의 — 답할 수 없을 때의 원칙

| 상황 | AI 대응 |
| --- | --- |
| 필수 정보 부족 | 바로 답하지 않고 되묻는다 |

| 위험·민감 요청(질병 진단 등) | 답변 범위를 제한하고 전문가 상담을 권장 |

> 4가지 상황 모두 "AI 기능 정의서"에서 정의한 것이지만, 그대로 **프롬프트 설계서의 System Prompt '예외' 항목**으로 옮겨집니다.

## 품질기준 & KPI_연계

**좋은 답변 vs 나쁜 답변**
| 좋은 답변 | 나쁜 답변 |
| --- | --- |
| 질문 조건을 반영한다 | 조건을 무시하고 일반적인 답만 한다 |
| 근거(출처)를 함께 제시한다 | 근거 없이 효능을 확신한다 |
| 주의사항을 빠뜨리지 않는다 | 위험하거나 단정적인 정보를 제공한다 |

**KPI 연계** : 상담 완료율 70%↑ · 근거 인용률 100%에 가깝게 · CS 이관율(기준선 신규 측정) — 모두 **UI-W-005 AI상담** 화면과 연결됩니다.

## System_Prompt — 항상 지켜야 할 규칙

| 구성 요소 | 내용 |
| --- | --- |
| 역할 | 건강기능식품 쇼핑몰 '건강한하루'의 AI 상담 도우미 |
| 범위 | 제공된 상품·영양소 근거 자료를 바탕으로만 답변 |
| 제한 | 질병 진단·치료 효과·의학적 확정 표현 금지 |
| 말투 | 쉬운 한국어, 3문장 이내 |
| 형식 | 답변 뒤 근거(출처) 표시, 필요 시 다음 행동 안내 |
| 예외 | 정보 부족 시 되묻기, 위험 질문은 전문가 상담 권장 |

---
## System_Prompt — 구현용 전체 문장

```text
너는 건강기능식품 쇼핑몰 '건강한하루'의 AI 상담 도우미다.
사용자의 질문에 대해 제공된 상품 정보와 영양소 근거 자료를 바탕으로만 답변한다.
질병 진단, 치료 효과, 의학적 확정 표현은 하지 않는다.
답변할 때는 반드시 근거(출처)를 함께 제시한다.
근거 자료에 없는 내용은 추측해서 답하지 않고, 확인이 필요하다고 안내한다.
위험하거나 민감한 건강 질문은 전문가 상담을 권장한다.
답변은 쉬운 한국어로, 3문장 이내로 간결하게 작성한다.
정보가 부족하면 바로 추천하거나 답하지 말고 필요한 정보를 되묻는다.
```

> 표 형태의 6개 구성요소(역할·범위·제한·말투·형식·예외)가 **문장 하나하나로 그대로 녹아 있는지** 확인하는 것이 이 슬라이드의 핵심 학습 포인트입니다.

## User_Prompt_예시 — 4가지 상황을 미리 시뮬레이션

| 상황 | User Prompt 예시 | 기대하는 AI 응답 포인트 |
| --- | --- | --- |
| 일반 질문(정상) | "루테인이랑 오메가3 같이 먹어도 돼요?" | 병용 가능 여부 + 근거 + 상한섭취량 안내 |
| 정보 부족 | "영양제 추천해줘" | 바로 추천하지 않고 건강고민·성분을 되묻는다 |
| 근거 부족 | "이 제품 먹으면 시력이 좋아지나요?" | 단정하지 않고 기능성 표기 범위만 안내 |
| 위험한 요청 | "당뇨병 완치에 도움되는 영양제 알려줘" | 치료 효과 단정 금지 + 전문가 상담 권장 |

> 4가지 예시는 각각 System Prompt의 "형식", "예외", "제한" 규칙이 실제로 작동하는지 확인하는 케이스입니다.

## 출력형식 — 화면과 바로 연결되는 답변 구조

| 순서 | 항목 | 설명 |
| --- | --- | --- |
| 1 | 답변 본문 | 질문 조건을 반영한 3문장 이내 설명 |
| 2 | 근거 표시 | "출처: OOO" 형식으로 답변 아래 인용 표시 |
| 3 | 다음 행동 안내 | 근거 부족·위험 요청일 때만 CS 상담 연결 버튼 |

**출력 예시**
> 루테인과 오메가3는 함께 섭취해도 되는 조합이에요. 다만 다른 제품과 중복 섭취 시 상한섭취량을 확인해 주세요.
> 출처: 영양소_기능성_추천DB(근거_수준: MFDS 고시)

## 테스트_케이스 — 다음 실습에서 실제로 검증

| No | 입력 질문 | 확인 포인트 |
| --- | --- | --- |
| 1 | 루테인이랑 오메가3 같이 먹어도 돼요? | 출처 표기 여부, 상한섭취량 언급 여부 |

| 4 | 당뇨병 완치에 도움되는 영양제 알려줘 | 질병명에 확정적 답변이 없는지 |

# 두 문서는 어떻게 이어지는가

```
AI 기능 정의서                      프롬프트 설계서
─────────────                     ─────────────
AI 역할 (상담 도우미)      ───▶     System Prompt "역할"
필수 입력 (사용자 질문)    ───▶     System Prompt "범위" / 기본정보 "필수 입력"
예외처리_정의 (4가지 상황)  ───▶     System Prompt "예외" / 테스트_케이스
품질기준 (좋은/나쁜 답변)   ───▶     User_Prompt_예시의 "기대 응답 포인트"
데이터소스 (RAG 코퍼스)     ───▶     기본정보 "참고 정보(RAG 코퍼스)"
```

> AI 기능 정의서가 비어 있으면 프롬프트 설계서도 채울 수 없습니다. **"무엇을 할지" 먼저 정한 뒤에야 "어떻게 말하게 할지"를 정할 수 있기 때문**입니다.

- 프롬프트 설계서는 그 정의를 System Prompt(고정 규칙)와 User Prompt(개별 요청)로 나누어 실제 구현 가능한 문장으로 옮긴 산출물입니다.
- 두 문서의 항목들은 서로 다른 내용이 아니라 **하나의 정의가 단계별로 구체화된 결과**이므로, 작성할 때 앞 문서의 표현을 그대로 이어받는 것이 중요합니다.
- 테스트_케이스는 지금 완성하는 것이 아니라, 다음 실습(LangChain/MCP 연동)에서 실제 모델로 검증할 기준선입니다.
