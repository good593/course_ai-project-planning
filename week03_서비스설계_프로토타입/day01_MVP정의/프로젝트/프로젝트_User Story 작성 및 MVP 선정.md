# Day 01 프로젝트 실습

## 건강한하루 User Story 작성 및 MVP 선정

> Week01~02에서 정리한 Pain Point, 가설·KPI, 요구사항정의서(RF-1~4)를 바탕으로, **"건강한하루"** 의 User Story를 작성하고 MoSCoW로 첫 버전(MVP)의 범위를 선정합니다.

---
## 실습 목표
- 기능적 요구사항(RF-1~4)을 사용자 관점의 User Story로 다시 쓴다.
- 공급자 관점 표현을 사용자 관점 표현으로 바꾼다.
- 기능 후보를 사용자 흐름 단위로 묶는다.
- MoSCoW로 기능 우선순위를 나누고 MVP(Must have) 범위를 확정한다.

---
## 실습 흐름
```
Week01 요구사항정의서(RF-1~4) 확인
  ↓
Week02 수집 데이터 확인
  ↓
User Story 작성
  ↓
기능 후보를 사용자 흐름 단위로 정리
  ↓
MoSCoW 우선순위 분류
  ↓
MVP(Must have) 범위 확정
```

## 요구사항정의서 4대 핵심 기능 (RF-1~4)
| 기능 | 대표 요구사항 |
| --- | --- |
| RF-1.0 AI 맞춤 상품 추천 | 건강고민 입력 → 맞춤 추천(최대 5개) → 추천 근거 표시 → 재추천 요청 |
| RF-2.0 AI 성분 설명 | 어려운 영양소 용어를 쉬운 설명 + 출처 표기 |
| RF-3.0 AI 상담/RAG FAQ | 자연어 상담 → RAG 답변 생성 → 근거 문서 인용 → CS 이관 분기 |
| RF-4.0 복용 정보 안내 | 권장/상한 섭취량 표시 → 과다섭취 경고 → AI는 설명 보조 |

> 오늘은 이 네 기능을 사용자 문장(User Story)으로 바꾸고, 그중 첫 버전에 반드시 있어야 할 기능만 골라냅니다.

---
## Day04 가설·KPI 요약 (User Story 작성의 근거)
| Pain Point | 가설 | AI 적용 가능성 |
| --- | --- | --- |
| 종류가 너무 많아 선택이 어렵다 | 맞춤 추천을 제공하면 선택 소요 시간이 줄어든다 | AI 적합 |
| 증상에 맞는 영양소를 모른다 | 쉬운 설명을 제공하면 재질문이 줄어든다 | AI 적합 |
| 정보가 여러 사이트에 분산되어 있다 | RAG 답변을 제공하면 상담 완료율이 높아진다 | AI 적합(근거 인용 필수) |
| 맞는 영양제를 추천받기 어렵다 | 복용 정보를 안내하면 CS 문의가 줄어든다 | 규칙 기반 우선 + AI 설명 보조 |

# 1단계. 공급자 관점 → 사용자 관점 바꾸기

---
## 건강한하루 기능명, 이대로 쓰면 안 되는 이유
나쁜 예시(공급자 관점):

> AI가 영양제를 추천한다.
> RAG 기반 상담 챗봇을 제공한다.
> 권장/상한 섭취량을 표시한다.

이 표현에는 **누가, 왜** 필요한지가 빠져 있습니다.  
User Story로 바꾸면 사용자 상황과 가치가 드러납니다.

---
## 공급자 관점 → 사용자 관점 변환
| 공급자 관점 | 사용자 관점 |
| --- | --- |
| AI 맞춤 상품 추천 제공 | 사용자가 4만 개가 넘는 제품 중에서 고민 없이 후보를 좁힌다 |
| AI 성분 설명 제공 | 사용자가 낯선 영양소 용어를 다시 찾아보지 않고 바로 이해한다 |
| RAG 상담 챗봇 제공 | 사용자가 여러 사이트를 돌아다니지 않고 한 곳에서 근거 있는 답을 얻는다 |
| 복용 정보 안내 제공 | 사용자가 여러 제품을 함께 먹어도 되는지 안심하고 확인한다 |

---
# 2단계. User Story 작성

---
## User Story 형식
> 나는 [사용자]로서  
> [원하는 행동]을 하고 싶다.  
> 그래서 [얻고 싶은 가치]를 얻을 수 있다.

RF-1~4 각각을 이 형식으로 다시 씁니다.

---
## RF-1.0 AI 맞춤 상품 추천 — User Story
> 나는 4만 개가 넘는 건강기능식품 중 무엇을 골라야 할지 모르는 사용자로서,  
> 내 건강 고민(예: 눈 피로, 피로감)을 입력하면 관련 영양소와 제품을 추천받고 싶다.  
> 그래서 제품을 하나하나 비교하는 시간을 줄이고 확신을 가지고 선택할 수 있다.

관련 데이터: 상품마스터.csv, 영양소_기능성_추천DB_확장판.csv

---
## RF-2.0 AI 성분 설명 — User Story
> 나는 영양소 용어가 낯선 사용자로서,  
> 어려운 성분명과 기능성을 쉬운 말로 설명받고 싶다.  
> 그래서 상품 상세페이지에서 다시 검색하거나 CS에 문의하지 않고 바로 이해할 수 있다.

관련 데이터: 영양소_기능성_추천DB_확장판.csv(근거_수준, 근거_설명, 출처)

---
## RF-3.0 AI 상담/RAG FAQ — User Story
> 나는 영양제 정보가 여러 사이트에 흩어져 있어 지친 사용자로서,  
> 궁금한 점을 한 곳에 물어보고 식약처 근거가 담긴 답변을 받고 싶다.  
> 그래서 정보를 신뢰하고 상담을 빠르게 끝낼 수 있다.

관련 데이터: 상품마스터·영양소_기능성_추천DB·권장섭취량 데이터를 RAG 코퍼스로 재사용

---
## RF-4.0 복용 정보 안내 — User Story
> 나는 여러 제품을 함께 구매·복용하는 사용자로서,  
> 권장/상한 섭취량과 과다섭취 위험을 미리 안내받고 싶다.  
> 그래서 건강에 해가 되지 않게 안전하게 복용량을 조절할 수 있다.

관련 데이터: 영양소별_권장섭취량_확장판_한글.csv, 상품마스터.csv

---
## User Story 점검
네 가지 User Story 모두 세 요소를 갖추고 있는지 확인합니다.

| 기능 | 사용자 | 원하는 행동 | 얻는 가치 |
| --- | --- | --- | --- |
| RF-1 | 선택이 어려운 사용자 | 고민 입력 후 맞춤 추천 | 비교 시간 단축, 선택 확신 |
| RF-2 | 용어가 낯선 사용자 | 쉬운 성분 설명 | 재질문·문의 감소 |
| RF-3 | 정보가 분산돼 지친 사용자 | 근거 있는 상담 답변 | 신뢰, 빠른 상담 종료 |
| RF-4 | 여러 제품을 함께 먹는 사용자 | 섭취량·경고 안내 | 안전한 복용 |

# 3단계. 기능 후보를 사용자 흐름 단위로 정리

---
## 사용자 흐름 단위 묶기
| 기능 묶음 | 건강한하루 예시 |
| --- | --- |
| 사용 시작 | 홈 화면 진입, 건강 고민 카테고리 선택 |
| 정보 입력 | 건강 고민/증상 입력, (선택) 알레르기·복용 중 제품 입력 |
| 핵심 결과 | 맞춤 상품 추천, 추천 근거 표시 |
| 확인과 수정 | 성분 쉬운 설명 보기, 재추천 요청, RAG 상담으로 추가 질문 |
| 저장과 공유 | 섭취량·경고 확인, (추후) 관심 상품 저장 |
| 운영 관리 | 추천·상담·경고 이력 로그(CS팀·법무팀 확인용) |

> 화면 단위가 아니라 사용자가 겪는 순서로 묶어야 MVP 범위를 판단하기 쉽습니다.

---
# 4단계. MoSCoW 우선순위 분류

---
## 건강한하루 MoSCoW
| 구분 | 기능 | 이유 |
| --- | --- | --- |
| Must | 건강 고민 입력 → 맞춤 상품 추천(RF-1.1, 1.2) | 없으면 서비스의 핵심 가치(선택 시간 단축)가 성립하지 않음 |
| Must | 추천 근거 표시(RF-1.3) | 근거가 없으면 추천을 신뢰할 수 없음 |
| Must | 권장/상한 섭취량 표시(RF-4.1) | 건강 서비스에서 최소한의 안전 정보는 첫 버전부터 필요 |

---
| 구분 | 기능 | 이유 |
| --- | --- | --- |
| Should | AI 성분 설명(RF-2.0) | 이해를 돕지만, 없어도 추천→구매 흐름 자체는 작동함 |
| Should | 재추천 요청(RF-1.4) | 경험을 개선하지만 첫 검증의 필수 조건은 아님 |
| Could | AI 상담/RAG FAQ 자유 질의(RF-3.0) | 차별화 요소지만 구현·품질 검증 난이도가 높아 다음 단계에서 검증 |
| Could | CS 이관 분기(RF-3.4) | 상담 기능이 없으면 필요성도 함께 미뤄짐 |
| Won't | 여러 제품 합산 섭취량 과다경고(RF-4.2 전체) | 장바구니·복수 제품 로직까지 포함되어 첫 검증 범위를 넘음 |
| Won't | 관심 상품 저장, 개인 이력 관리 | 핵심 가치 검증과 무관, 로그인·개인화 인프라 필요 |

---
## Must have만으로 가치가 전달되는지 확인
Must have 세 가지(건강 고민 입력 → 맞춤 추천 → 추천 근거 → 섭취량 표시)만으로도

- 사용자가 자신의 문제(선택 어려움)를 해결해 볼 수 있는가? → **가능**
- 서비스의 핵심 흐름이 처음부터 끝까지 이어지는가? → **가능** (입력 → 추천 → 확인)
- 결과가 사용자의 판단(구매 여부)에 도움을 주는가? → **가능**
- 피드백을 받을 수 있을 만큼 구체적인가? → **가능**

→ Must have만으로도 Viable한 MVP 조건을 충족합니다.

# 5단계. MVP 정의문 작성

---
## 약한 설명 vs 좋은 설명
약한 설명:

> AI 기반 건강기능식품 추천 앱을 만든다.

좋은 설명:

> 건강기능식품 종류가 너무 많아 선택이 어려운 사용자가  
> 자신의 건강 고민을 입력하면 근거가 담긴 맞춤 상품을 추천받고,  
> 권장·상한 섭취량까지 함께 확인해 안전하게 구매를 결정할 수 있는  
> 첫 버전을 만든다.

---
## 건강한하루 MVP 정의문
> **바쁘고 지식이 부족한 사용자가 건강 고민을 입력하면,**  
> **AI가 근거(기능성·출처)와 함께 맞춤 상품을 최대 5개 추천하고,**  
> **제품별 권장·상한 섭취량을 함께 보여주어**  
> **사용자가 비교 시간을 줄이고 안전하게 첫 구매를 결정할 수 있게 하는 서비스.**

AI 성분 설명, RAG 상담, 복수 제품 섭취량 경고는 MVP 검증 이후 순차 확장합니다.

---
## MVP 범위와 KPI 연결
| Must have 기능 | 관련 KPI(Day04) |
| --- | --- |
| 맞춤 상품 추천 | 추천 후 상세페이지 진입까지 평균 소요 시간 30% 감소(4주) |
| 추천 근거 표시 | 추천 결과 클릭률(선행지표) |
| 섭취량 표시 | 과다 섭취 관련 CS 문의 25% 감소(4주, 단일 제품 기준) |

> MVP 범위를 좁혀도 KPI 검증에 필요한 지표는 그대로 측정할 수 있어야 합니다.

---
# 정리
- User Story는 RF-1~4를 "누가·무엇을·왜"가 보이는 사용자 문장으로 바꾸는 작업입니다.
- 기능 후보는 화면이 아니라 사용자 흐름(시작→입력→결과→확인→저장→운영) 단위로 묶습니다.
- MoSCoW는 모든 기능을 중요하다고 말하지 않기 위한 도구이며, Must have는 적을수록 좋습니다.
- 건강한하루의 MVP는 **"건강 고민 입력 → 근거 기반 맞춤 추천 → 섭취량 확인"** 흐름이며, AI 성분 설명·RAG 상담·복수 제품 경고는 검증 이후로 미룹니다.
