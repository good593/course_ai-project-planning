## 오늘의 핵심 질문

RAG 서비스 기획에서 가장 먼저 정해야 할 것은 기술이 아닙니다.

기획자는 다음 질문에 답해야 합니다.

- 어떤 사용자 문제를 RAG로 해결할 것인가?
- 어떤 질문에 답하게 할 것인가?
- 어떤 문서와 데이터를 근거로 사용할 것인가?
- 어디까지 답하고 어디서 멈출 것인가?
- 사용자는 답변의 근거를 어떻게 확인할 것인가?

RAG 기획은 **AI가 참고할 지식의 범위와 답변 책임을 정하는 일**입니다.

---

## RAG 서비스 기획이란?

RAG 서비스 기획은 AI 채팅 기능을 넣는 일이 아닙니다.

RAG 서비스 기획은 다음을 정리하는 과정입니다.

| 기획 항목 | 의미 |
|---|---|
| 사용자 질문 | 어떤 질문에 답할 것인가 |
| 참고 지식 | 어떤 문서와 데이터를 사용할 것인가 |
| 답변 방식 | 어떻게 설명하고 근거를 보여줄 것인가 |
| 제한 범위 | 어떤 질문에는 답하지 않을 것인가 |
| 실패 안내 | 근거가 없을 때 어떻게 안내할 것인가 |

RAG는 "검색 가능한 지식"을 서비스 기능으로 바꾸는 설계입니다.

---

## 왜 기능 정의가 먼저 필요한가?

RAG는 문서를 많이 넣는다고 좋은 기능이 되지 않습니다.

기능 정의가 없으면 다음 문제가 생깁니다.

- 어떤 질문에 답해야 하는지 불명확함
- 관련 없는 문서까지 검색 대상에 포함됨
- 답변의 기준과 한계가 흐려짐
- 출처 표시 방식이 일관되지 않음
- 품질 평가 기준을 세우기 어려움

기능 정의는 RAG가 해야 할 일과 하지 말아야 할 일을 구분해 줍니다.

---

## RAG 기능 정의란?

RAG 기능 정의는 사용자에게 제공할 RAG 기능의 역할을 문장으로 정리하는 것입니다.

좋은 기능 정의는 다음 요소를 포함합니다.

- 대상 사용자
- 사용자가 묻는 질문 유형
- 참고할 문서 또는 데이터
- AI가 제공할 답변 형태
- 답변의 제한 조건
- 사용자가 얻는 가치

기능 정의는 개발 설명이 아니라 **서비스 약속을 정리한 문장**입니다.

---

## 기능 정의 문장 구조

RAG 기능은 다음 문장으로 정리할 수 있습니다.

> [사용자]가 [상황]에서 [질문/문제]를 해결할 수 있도록
> [근거 자료]를 검색해 [답변 형태]로 제공한다.

예시:

> 사용자가 상품 구매 전 성분과 주의사항을 확인할 수 있도록
> 상품 상세 문서와 FAQ를 검색해 근거가 포함된 답변을 제공한다.

이 문장은 기능의 목적, 데이터, 답변 방식을 한 번에 보여줍니다.

---

## RAG 기능 정의 항목

| 항목 | 작성 질문 |
|---|---|
| 사용자 | 누가 이 기능을 사용하는가? |
| 사용 상황 | 언제 이 기능이 필요한가? |
| 질문 유형 | 어떤 질문을 자주 하는가? |
| 참고 자료 | 어떤 문서를 근거로 삼는가? |
| 답변 형식 | 결론, 근거, 출처를 어떻게 보여주는가? |
| 제한 조건 | 어떤 내용은 답하지 않는가? |
| 성공 기준 | 사용자가 무엇을 해결하면 성공인가? |

이 항목이 정리되면 RAG 기능의 방향이 명확해집니다.

---

## 좋은 기능 정의와 아쉬운 기능 정의

| 구분 | 예시 |
|---|---|
| 아쉬운 정의 | 상품 정보를 알려주는 AI 챗봇 |
| 좋은 정의 | 사용자가 상품 구매 전 성분, 섭취 방법, 주의사항을 확인할 수 있도록 상품 상세 문서와 FAQ를 근거로 답변하는 기능 |

아쉬운 정의는 기능이 넓고 모호합니다.

좋은 정의는 **누구에게, 어떤 질문에, 어떤 근거로, 어떤 답변을 줄지**가 보입니다.

---

## RAG 적용 범위란?

RAG 적용 범위는 AI가 답변할 수 있는 영역과 답변하지 않아야 할 영역을 정하는 것입니다.

적용 범위를 정하면 다음이 명확해집니다.

- 어떤 문서를 검색 대상으로 포함할지
- 어떤 질문까지 답변할지
- 어떤 질문은 안내만 하고 멈출지
- 어떤 답변에는 출처 표시가 필요한지
- 어떤 경우에는 사람의 확인이 필요한지

RAG 적용 범위는 서비스 신뢰도를 지키는 울타리입니다.

---

## 적용 범위 설계 기준

RAG 적용 범위는 다음 기준으로 정합니다.

| 기준 | 확인 질문 |
|---|---|
| 사용자 가치 | 자주 묻고 해결 가치가 큰 질문인가? |
| 데이터 존재 | 답변 근거가 되는 문서가 있는가? |
| 최신성 관리 | 문서를 계속 관리할 수 있는가? |
| 위험도 | 잘못 답하면 사용자 피해가 큰가? |
| 출처 필요성 | 답변에 근거 표시가 필요한가? |
| 운영 가능성 | 품질 평가와 개선이 가능한가? |

적용 범위는 넓게 잡기보다 안정적으로 답할 수 있는 영역부터 정합니다.

---

## In Scope와 Out of Scope

적용 범위는 포함할 것과 제외할 것을 함께 정리해야 합니다.

| 구분 | 의미 |
|---|---|
| In Scope | RAG가 답변해야 하는 질문과 기능 범위 |
| Out of Scope | RAG가 답변하지 않거나 제한해야 하는 범위 |

---
예를 들어 상품 정보 RAG라면 다음처럼 나눌 수 있습니다.

| In Scope | Out of Scope |
|---|---|
| 상품 성분 설명 | 질병 진단 |
| 섭취 방법 안내 | 치료 효과 단정 |
| 주의사항 요약 | 개인 건강 상태 판단 |
| FAQ 기반 답변 | 문서에 없는 추천 |

제외 범위를 정하는 것도 중요한 기획입니다.

---

## 답변 가능 범위 정하기

RAG는 모든 질문에 답하려고 하면 위험해집니다.

기획자는 질문을 세 가지로 나눌 수 있습니다.

| 질문 유형 | 처리 방식 |
|---|---|
| 답변 가능 | 문서 근거로 답변하고 출처를 표시함 |
| 조건부 답변 | 문서 범위 안에서만 답하고 한계를 안내함 |
| 답변 불가 | 근거가 없거나 위험한 질문은 안내 후 중단함 |

답변 불가는 기능 실패가 아니라 신뢰를 지키는 설계입니다.

---

## 근거 표시 방식 설계

RAG 답변은 사용자가 근거를 확인할 수 있어야 합니다.

기획자는 다음을 정해야 합니다.

- 답변 아래에 출처 문서를 보여줄 것인가
- 문서 제목과 날짜를 함께 보여줄 것인가
- 상품명, 카테고리 같은 기준 정보를 보여줄 것인가
- 근거가 여러 개일 때 우선순위를 어떻게 보여줄 것인가
- 근거가 부족할 때 어떤 문구로 안내할 것인가

근거 표시는 RAG 답변의 신뢰를 만드는 중요한 화면 요소입니다.

---

## 실패 상황 설계

RAG는 항상 좋은 문서를 찾는 것이 아닙니다.

따라서 실패 상황을 미리 설계해야 합니다.

| 상황 | 안내 방향 |
|---|---|
| 관련 문서 없음 | 확인된 자료가 없다고 안내 |
| 문서가 오래됨 | 최신 정보 확인 필요 안내 |
| 질문이 모호함 | 필요한 정보를 다시 질문 |
| 문서끼리 충돌함 | 단정하지 않고 확인 필요 안내 |
| 위험한 판단 요청 | 제한 범위를 설명하고 중단 |

좋은 RAG 서비스는 실패했을 때도 사용자가 다음 행동을 알 수 있습니다.

---

## RAG 기능 정의서에 들어갈 내용

RAG 기능 정의서는 다음 항목으로 정리할 수 있습니다.

| 항목 | 내용 |
|---|---|
| 기능명 | 사용자가 이해할 수 있는 기능 이름 |
| 목적 | 어떤 문제를 해결하는가 |
| 대상 사용자 | 누가 사용하는가 |

---
| 항목 | 내용 |
|---|---|
| 대표 질문 | 사용자가 입력할 질문 예시 |
| 참고 자료 | 검색에 사용할 문서와 데이터 |
| 답변 형식 | 결론, 근거, 출처, 주의사항 |
| 적용 범위 | 답변할 질문과 제외할 질문 |
| 성공 기준 | 기능이 잘 동작했다고 판단할 기준 |

기능 정의서는 RAG 구현 전에 방향을 맞추는 기준 문서가 됩니다.

---

## 기능 범위가 너무 넓을 때의 문제

RAG 적용 범위를 너무 넓게 잡으면 다음 문제가 생깁니다.

- 검색 대상 문서가 많아져 관련성이 떨어짐
- 답변 기준이 흔들림
- Hallucination 가능성이 커짐
- 품질 평가가 어려워짐
- 사용자가 기능을 어떻게 써야 할지 헷갈림

처음부터 모든 질문에 답하는 RAG보다
명확한 질문 범위에서 신뢰도 높게 답하는 RAG가 더 좋습니다.

---

## 적용 범위 우선순위

RAG 적용 범위는 다음 순서로 넓혀가는 것이 좋습니다.

1. 근거 문서가 명확한 질문
2. 사용자 빈도가 높은 질문
3. 답변 오류 위험이 낮은 질문
4. 출처 표시로 신뢰를 높일 수 있는 질문
5. 품질 평가가 가능한 질문

처음 범위는 작아도 괜찮습니다.
중요한 것은 사용자가 믿고 반복해서 쓸 수 있는 범위를 찾는 것입니다.

---

## 오늘의 정리

RAG 서비스 기획은 기능 정의와 적용 범위 설계로 시작합니다.

오늘의 핵심은 두 가지입니다.

1. RAG 기능 정의는 사용자, 질문, 근거 자료, 답변 형식을 명확히 하는 일이다
2. RAG 적용 범위 설계는 답변할 영역과 답변하지 않을 영역을 정하는 일이다

기획자의 역할은 RAG를 넓게 붙이는 것이 아니라
**사용자가 신뢰할 수 있는 질문 범위와 답변 기준을 설계하는 것**입니다.
