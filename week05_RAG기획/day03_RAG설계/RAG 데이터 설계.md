# RAG 데이터 설계

AI가 참고할 문서를 어떻게 고르고 정리할 것인가

---

## 오늘의 전제

이전 수업에서 RAG 서비스 구조를 배웠습니다.

오늘은 Retriever, Vector DB, LLM의 구조를 다시 설명하기보다
그 구조 안에 들어갈 **데이터를 어떻게 설계할지**에 집중합니다.

기획자가 정해야 할 질문은 이것입니다.

> AI가 답변할 때 믿고 참고해도 되는 자료는 무엇인가?

---

## 오늘의 핵심 질문

RAG 데이터 설계는 문서를 많이 넣는 일이 아닙니다.

기획자는 다음을 판단해야 합니다.

- 어떤 문서를 넣을 것인가?
- 어떤 문서는 제외할 것인가?
- 문서를 어떤 단위로 나눌 것인가?
- 문서 조각에 어떤 설명 정보를 붙일 것인가?
- 오래된 문서와 충돌하는 문서는 어떻게 관리할 것인가?

RAG의 답변 품질은 데이터 준비 방식에서 크게 달라집니다.

---

## RAG 데이터 설계란?

RAG 데이터 설계는 AI가 참고할 지식을
검색하기 좋은 형태로 정리하는 일입니다.

쉽게 말하면,

> 서비스 안의 문서를 AI가 찾아보고 답할 수 있도록
> 기준을 세우고 구조화하는 과정입니다.

문서가 부정확하거나 정리되어 있지 않으면
AI도 부정확한 근거를 보고 답하게 됩니다.

---

## 서비스 질문에서 출발하기

데이터 설계는 문서 목록보다 사용자 질문에서 시작합니다.

예를 들어 건강기능식품 쇼핑몰이라면
사용자는 이런 질문을 할 수 있습니다.

- 이 제품을 임산부가 먹어도 되나요?
- 알레르기 유발 성분이 있나요?
- 하루에 몇 번 먹어야 하나요?
- 다른 제품과 무엇이 다른가요?
- 환불이나 교환이 가능한가요?

질문을 먼저 정리해야 필요한 문서가 보입니다.

---

## 질문과 근거 문서 연결하기

사용자 질문마다 필요한 근거 문서는 다를 수 있습니다.

| 사용자 질문 | 필요한 근거 문서 |
|---|---|
| 복용 가능 여부 | 성분표, 주의사항, FAQ |
| 섭취 방법 | 상품 설명, 섭취 가이드 |
| 부작용 우려 | 주의사항, 전문가 안내 문구 |
| 배송/환불 | 배송 정책, 교환/환불 정책 |
| 제품 비교 | 상품별 성분, 가격, 대상 고객 |

RAG 데이터 설계의 첫 단계는
**질문과 근거 문서를 짝지어 보는 것**입니다.

---

## 넣을 문서와 제외할 문서

RAG에 넣을 문서는 답변 근거가 될 수 있어야 합니다.

| 구분 | 판단 기준 |
|---|---|
| 넣을 문서 | 사용자 질문에 직접 답할 수 있음 |
| 보류할 문서 | 내용은 유용하지만 최신성이나 출처 확인이 필요함 |
| 제외할 문서 | 오래되었거나 중복, 충돌, 비공개 정보가 포함됨 |

문서를 많이 넣으면 좋아지는 것이 아니라
**믿을 수 있는 문서를 넣어야** 좋아집니다.

---

## 좋은 RAG 문서의 조건

RAG에 적합한 문서는 다음 조건을 갖습니다.

- 질문에 대한 답이나 판단 근거가 들어 있음
- 작성 기준과 출처가 명확함
- 최신 상태로 관리될 수 있음
- 중복되거나 서로 충돌하는 내용이 적음
- 제목, 항목, 조건, 예외가 구분되어 있음
- 사용자에게 공개해도 되는 내용만 포함함

AI에게 보여줄 문서는 내부 보관용 문서와 기준이 다를 수 있습니다.

---

## 문서 목록표 만들기

기획자는 먼저 사용할 문서를 목록화합니다.

| 문서명 | 문서 유형 | 답할 수 있는 질문 | 관리 부서 | 공개 가능 여부 |
|---|---|---|---|---|
| 상품 상세 설명 | 상품 정보 | 성분, 섭취 방법 | 상품팀 | 가능 |
| 섭취 주의사항 | 안전 안내 | 임산부, 알레르기 | 품질팀 | 가능 |
| 상담 매뉴얼 | 고객지원 | 예외 상황 대응 | CS팀 | 일부 가능 |
| 내부 승인 기준 | 운영 기준 | 판매 가능 여부 | 운영팀 | 불가 |

문서 목록표는 개발 전에 만드는 데이터 설계의 출발점입니다.

---

## 문서 관리 기준

RAG에서는 오래된 문서도 답변 근거가 될 수 있습니다.

그래서 문서마다 관리 기준이 필요합니다.

| 관리 항목 | 확인 질문 |
|---|---|
| 소유자 | 이 문서는 누가 관리하는가? |
| 업데이트 주기 | 언제 최신화되는가? |
| 버전 | 이전 내용과 최신 내용을 구분할 수 있는가? |
| 공개 범위 | 사용자가 봐도 되는 정보인가? |
| 삭제 기준 | 더 이상 쓰지 않는 문서는 어떻게 제외하는가? |
| 충돌 기준 | 문서끼리 다르면 무엇을 우선할 것인가? |

---

## 청킹을 바라보는 관점

청킹은 문서를 작게 자르는 기술 작업처럼 보일 수 있습니다.

하지만 기획 관점에서는
**사용자 질문에 답하기 좋은 단위로 문서를 나누는 일**입니다.

예를 들어 하나의 상품 상세 페이지도
다음 정보는 따로 다루는 편이 좋습니다.

- 상품 기본 정보
- 주요 성분
- 섭취 방법
- 섭취 주의사항
- 자주 묻는 질문

---

## Chunk를 나누는 기준

좋은 Chunk는 하나의 질문에 답할 만큼 충분해야 합니다.

| 나누는 기준 | 적합한 문서 |
|---|---|
| 제목 기준 | 매뉴얼, 정책 문서 |
| 질문 기준 | FAQ, 상담 스크립트 |
| 항목 기준 | 상품 정보, 성분표, 비교표 |
| 조건 기준 | 환불 조건, 예외 정책, 주의사항 |

기준은 문서 모양이 아니라
**사용자가 어떤 질문을 할지**에 맞춰 정합니다.

---

## 좋지 않은 Chunk 예시

Chunk를 잘못 나누면 검색 결과가 흔들립니다.

| 문제 | 사용자 경험 |
|---|---|
| 너무 크게 나눔 | 관련 없는 정보까지 답변에 섞임 |
| 너무 작게 나눔 | 필요한 조건이나 예외가 빠짐 |
| 제목 없이 나눔 | 어떤 문서의 내용인지 알기 어려움 |
| 표를 중간에 자름 | 기준, 수치, 조건이 끊어짐 |
| 서로 다른 주제를 섞음 | 답변이 모호하거나 틀릴 수 있음 |

Chunk 하나만 봐도 무슨 내용인지 알 수 있어야 합니다.

---

## Chunk 설계 예시

원문:

> 비타민D 1000IU는 하루 1회 섭취합니다. 임산부, 수유부, 특정 질환이 있는 경우 전문가와 상담 후 섭취하세요.

좋은 Chunk:

| 항목 | 내용 |
|---|---|
| 제목 | 비타민D 1000IU 섭취 방법 및 주의사항 |
| 본문 | 하루 1회 섭취. 임산부, 수유부, 특정 질환자는 전문가 상담 필요 |
| 답할 질문 | 복용량, 임산부 섭취 가능 여부, 주의 대상 |

단순히 길이로 자르기보다 답변 단위로 정리합니다.

---

## 메타데이터란?

메타데이터는 문서 조각에 붙이는 설명 정보입니다.

AI가 문서를 찾을 때 검색 범위를 좁히고, 사용자에게 출처를 보여주기 위해 필요합니다.

| 메타데이터 | 예시 |
|---|---|
| 문서 유형 | 상품 설명, FAQ, 정책 |
| 상품명 | 비타민D 1000IU |
| 카테고리 | 영양제, 뼈 건강 |
| 작성일 | 2026-07-01 |
| 관리 부서 | 상품팀 |
| 공개 범위 | 전체 사용자 공개 |

---

## 메타데이터를 설계할 때 볼 것

메타데이터는 많이 붙이는 것보다 검색과 운영에 실제로 쓰이는 것이 중요합니다.

기획자는 다음을 확인합니다.

- 사용자가 상품명이나 카테고리로 질문하는가?
- 최신 문서를 우선해야 하는가?
- 사용자 권한에 따라 보여줄 문서가 달라지는가?
- 답변에 출처 제목이나 URL을 보여줘야 하는가?
- 특정 부서가 관리하는 문서를 구분해야 하는가?

메타데이터는 검색 품질과 서비스 운영을 함께 돕습니다.

---

## 출처 정보 설계

RAG 답변은 근거를 보여줄 수 있어야 신뢰를 얻습니다.

| 항목 | 예시 |
|---|---|
| 문서 제목 | 비타민D 1000IU 상품 상세 |
| 문서 위치 | 상품 상세 페이지 URL |
| 작성일/수정일 | 2026-07-01 |
| 담당 부서 | 상품팀 |
| 사용자 표시명 | 제품 상세 설명 |

내부 파일명 그대로 보여주기보다 사용자가 이해할 수 있는 출처명으로 설계해야 합니다.

---

## 권한과 민감 정보

RAG 데이터에는 사용자에게 보여주면 안 되는 정보가 섞일 수 있습니다.

예를 들어 다음 정보는 주의가 필요합니다.

- 내부 원가, 마진, 협상 내용
- 직원 개인정보 또는 고객 개인정보
- 공개 전 상품 정보
- 내부 승인 기준이나 비공개 운영 정책
- 법무, 의료, 금융 판단처럼 오해 위험이 큰 내용

RAG 데이터 설계에서는
**검색되면 안 되는 정보**도 함께 정의해야 합니다.

---

## 충돌하는 문서 처리

문서마다 내용이 다르면 AI 답변도 흔들립니다.

예를 들어 한 문서에는 "7일 이내 환불 가능",
다른 문서에는 "14일 이내 환불 가능"이라고 적혀 있다면
AI는 어떤 기준으로 답해야 할지 알기 어렵습니다.

기획자는 다음 기준을 정해야 합니다.

- 최신 문서를 우선할 것인가?
- 정책 문서를 상품 설명보다 우선할 것인가?
- 담당 부서 승인 문서만 사용할 것인가?
- 충돌 시 답변하지 않고 확인 안내를 할 것인가?

---

## 정보가 없을 때의 처리

RAG 데이터에 답이 없는 질문도 들어올 수 있습니다.

이때 AI가 그럴듯하게 답하면 위험합니다.

기획자는 다음 안내 방식을 정해야 합니다.

| 상황 | 안내 방향 |
|---|---|
| 관련 문서 없음 | 확인된 자료가 없다고 안내 |
| 문서가 부족함 | 상담 또는 추가 확인 경로 안내 |
| 문서가 충돌함 | 단정하지 않고 기준 확인 필요 안내 |
| 권한이 없음 | 접근 가능한 범위에서만 답변 |

좋은 RAG는 모르는 것을 모른다고 말할 수 있어야 합니다.

---

## RAG 데이터 설계서에 들어갈 내용

| 항목 | 작성 내용 |
|---|---|
| 대표 질문 | 사용자가 자주 물을 질문 |
| 근거 문서 | 질문에 답할 문서 목록 |
| 포함/제외 기준 | 사용할 문서와 제외할 문서 기준 |
| Chunk 기준 | 문서를 나누는 단위 |
| 메타데이터 | 검색과 출처 표시에 필요한 정보 |
| 관리 기준 | 업데이트, 삭제, 충돌 처리 방식 |
| 실패 안내 | 답이 없을 때의 응답 원칙 |

이 표가 있으면 개발자와 데이터 준비 방향을 맞추기 쉽습니다.

---

## 데이터 품질 체크

RAG에 넣기 전 다음을 점검합니다.

| 기준 | 확인 질문 |
|---|---|
| 정확성 | 문서 내용이 사실과 맞는가? |
| 최신성 | 오래된 정보가 섞여 있지 않은가? |
| 완전성 | 대표 질문에 답할 수 있는가? |
| 구조화 | 제목, 항목, 조건이 구분되어 있는가? |
| 검색성 | 질문과 연결될 단위로 나뉘어 있는가? |
| 안전성 | 공개하면 안 되는 정보가 제거되었는가? |

데이터 품질은 RAG 답변 품질의 출발점입니다.

---

## 기획자가 마지막으로 확인할 질문

RAG 데이터 설계를 마치기 전에 다음을 점검합니다.

- 이 데이터로 사용자의 대표 질문에 답할 수 있는가?
- 답변 근거가 되는 문서가 명확한가?
- 문서 조각이 너무 크거나 작지 않은가?
- 검색에 필요한 메타데이터가 있는가?
- 최신 문서와 오래된 문서를 구분할 수 있는가?
- 사용자에게 보여주면 안 되는 정보가 제외되었는가?
- 답이 없을 때의 안내 원칙이 정해져 있는가?

---

## 오늘의 정리

RAG 데이터 설계는 AI가 참고할 지식을 준비하는 일입니다.

오늘의 핵심은 세 가지입니다.

1. 사용자 질문에서 출발해 필요한 근거 문서를 정한다
2. 문서를 답변하기 좋은 Chunk와 메타데이터로 정리한다
3. 최신성, 권한, 충돌, 실패 안내까지 운영 기준을 세운다

기획자의 역할은 문서를 많이 넣는 것이 아니라
**사용자 질문에 맞는 근거가 안전하게 찾아지도록 기준을 세우는 것**입니다.
